3. The workspace

The window has five parts. Once it is clear what lives where, the rest follows.

3.1 Title bar

At the top are the name of the case being worked on, Run and Stop. The case name is carried into the results and the report, so a recognisable name pays off.

3.2 Ribbon

The tabs are arranged in the order of the work.

TabWhat it does
HomePresets, saving and opening inputs, material database, machine settings (§3.7)
MaterialMatrix material and properties
StructureAdding and editing fillers and pores, Generate structure
DomainVoxel size, RVE size, accuracy level, Generate voxel grid
Structure AnalysisSwitches porosity, porosimetry, pore network, percolation and grain analysis on and off
SimulationSwitches the thermal, electrical, electromagnetic, mechanical and flow analyses on and off
DOEQueues many analyses at once from ranges of conditions
OptimizationKey factors, surrogate model, search for the optimum
CalibrationFinds unknown material values (interfacial resistance and others) from measured effective properties (chapter 30)
ResultsSwitching views, downloads, saving figures

The analysis icons of the ribbon show their on/off state. A click toggles them, exactly like the switches on the cards of the left panel. An analysis that cannot be used is greyed out (for example permeability without pores), with the reason.

The buttons that build the model are found only where the model is built: Generate structure in the Structure tab and Generate voxel grid in the Domain tab. The other tabs have only Run analyses and Stop.

3.3 Command panel (left)

Shows the inputs of the selected ribbon tab. Every change takes effect at once, and the information below it — the expected grid, the composition — updates immediately, so the settings can be checked before anything is run.

3.4 Central view

TabContent
3D / 2D ViewThe structure and the computed fields in 3D and in sections (chapter 26).
Result ViewerEvery numerical result, ordered by analysis (chapter 25).
DOETables and charts of the results per condition (chapter 28).
OptimizationBuilds a surrogate model (stage 1) and finds the optimum and the trade-off front with it (stage 2). Chapter 29.

3.5 Inspector (right)

Display sets what the 3D view shows — surfaces, sections, arrows, field lines, colour ranges and the colours and lighting of the phases (chapter 26). Runs lists the analyses run so far; clicking one shows it again. Each line tells what that run did — Structure when it only built a structure, otherwise a coloured tag per analysis (Thermal, Elastic/CTE, Viscosity, Moisture …), the grid and one line of the phases. A DOE case shows its variable values (for example "content 50 · d 5") instead of the phases, and a calibration a purple tag. Analyses made by a DOE are grouped into one line per study, which expands into the individual cases when clicked — even 64 cases at once do not bury the earlier results (chapter 28).

The list shows the analyses run from this browser. Each browser keeps its own mark in a cookie, so when several people share one server their lists do not mix. Analyses run with 6_RUN_COMMANDLINE.bat or a script, however, have no owner and are visible to everyone — by design, so that such results can be looked at together.

3.6 Dock (bottom)

Solver convergenceThe residual of the iterative solves falling; shows whether convergence is normal.

The status bar at the very bottom always shows the grid, the voxel size, the RVE size, the number of running and queued jobs and the current split of the cores.

3.7 Machine settings — parallel analyses and cores

The Machine section on the left of the Home tab decides how the computing resources of the PC are shared.

SettingMeaning
Analyses at once The number of analyses (jobs) run at the same time. The others wait in the queue.
Cores each The cores one analysis may use. 0 = automatic: a quarter of the PC, shared so that several analyses together never exceed the cores.

More cores for one solve — measured

PuMA's FE solve originally uses a single core: the grid's numbering tables are built in Python loops, and scipy's MINRES and NumPy's matrix products are single-threaded (measured on one 112³ thermal solve: 5.1 s for the tables, 3.4 s of MINRES vector work, 2.0 s of matrix products). v4 keeps PuMA's own equations (element matrices, periodic DOF numbering, loads, MINRES) and runs those three parts on all cores. Solved to the same tolerance, the result equals PuMA's original path within 1e-7, which the self-test checks every time (chapter 31).

One solve (14-core PC, fully converged)1 thread4814
Thermal FV (112³) — default1.4 s1.3 s1.4 s1.5 s
Thermal PuMA FE (112³) — optional30.5 s11.7 s8.4 s7.8 s
Elasticity PuMA FE (64³, one load)36.0 s13.7 s10.0 s8.3 s

The FE solve becomes about 4× faster on 14 threads and gains slowly from about 8 threads on, held back by the memory bandwidth. FV, the default for conduction, needs few iterations thanks to its FFT preconditioner (39) and takes 1.4 s on one thread — 20× faster than FE.

Splitting the cores — independent solves and threads inside a solve

Even within one analysis, every property, direction and elastic load is a separate solve. Thermal + dielectric + thermal expansion in x, y and z are 3 + 3 + 7 = 13 independent solves. The cores can be shared in two ways — several solves side by side, or several threads inside one solve. Side by side does more work per core (one elastic load: 36 core-seconds on 1 thread, 55 on 4), but when there are only a few long solves, such as elastic loads, threads finish sooner.

When an analysis starts, every possible split is evaluated and the one that finishes first is chosen. For each split the solves are assigned longest first and the finishing time is computed, with the speed-up of one solve given by S(t) = 1 / (0.15 + 0.85/t), fitted to the measurements above. The number of solves side by side is also limited by the free memory (Simulation tab, Independent solves, on by default).

Cores given to the analysis (13 solves)4812163264
Side by side × threads4 × 18 × 14 × 38 × 28 × 47 × 9

The run log (run.log) records it as, for example, parallel solves: 13 independent problems on 8 workers × 2 thread(s). When the memory allows fewer solves side by side, each gets more threads instead.

The results of the current method agree to the last digit (kx 0.462771 W/m·K, εx 5.19224, α = [36.128, 35.729, 35.965] ppm/K). The two early-v4 lines solved conduction with PuMA FE and placed the particles with Allow contacts, so their values differ. Most of the time is now spent on the seven elastic loads. On this PC the memory bandwidth is the limit from 12 cores on, so the way of splitting matters little. On a server with more memory channels the automatic split should gain more; running once with Independent solves Off and once with Auto on that server is recommended — the results are identical, only the times differ.

Tips.
• One analysis fast — raise Cores each. Both the solves side by side and the threads inside them increase.
• Many small DOE cases — raising Analyses at once is better; structure generation and post-processing overlap as well.

A changed setting applies from the next analysis that starts; running analyses are not touched.
When the set number of simultaneous runs is reached, the Run analyses button is greyed out and does not respond. Hovering over it shows why. When several people share one server through 3_RUN_SERVER.bat, the analyses of others count against this limit too — they occupy a slot even though they do not appear in your list, so a greyed-out button means waiting.

Memory is the other constraint. Running analyses in parallel multiplies the memory as well — three analyses that need 16 GB each need 48 GB together. The Domain tab tells how much one analysis needs (section 6.7).

The queue therefore also watches the memory before it starts the next analysis. To the memory estimate of the Domain tab it adds a measured margin (×1.4 + 0.3 GB); when the total with the analyses already running would exceed 70 % of the PC's memory, or the memory free right now is not enough, it waits before starting, even with a parallel slot free — once memory spills into the disk swap, every analysis slows down by an order of magnitude. A job running alone is never held back by this, so a large analysis cannot be blocked for ever.

The queue survives a server restart. Analyses that had not started are restored as queued after a restart and run in turn. Analyses interrupted mid-way are marked failed; DOE cases can be run again with the Re-run button of section 28.4.

3.8 Work folders and cases — where the results go

The two boxes Work folder and Case on the left of the Home tab decide where the results are written. Set them before running.

LevelWhat it isWhat appears on disk
Work folder A folder for one piece of work (a day, a project). Left empty when created, it is named with today's date. A name alone places it under the workspace; a full path can put it on another disk. workspace/2026-09-29/
Case One study inside the work folder. Every New case creates a folder, and all later analyses collect under this case. …/2026-09-29/hollow-sphere/
Analysis (run) One Run. The folder is named after what was analysed — not the time. Running the same analysis again adds -02, -03. …/hollow-sphere/thermal+dielectric/

The real folder of a study of hollow low-k fillers looks like this:

lowk_hollow_study/                  ← work folder
  knee-all-responses/               ← case
    thermal+dielectric+cte/         ← analysis: thermal + dielectric + thermal expansion
  size-distribution/
    thermal+dielectric/
    thermal+dielectric-02/          ← the same analysis again, with other conditions
    thermal+dielectric-03/
  doe-hollow-sphere/
    doe-HGM-t-0.526817-vf-29.1782/  ← DOE case: named by the values it changed
    doe-HGM-knee-t-1.018-vf-45.0/
The list shows only the analyses of the open work folder. The work folder and the case can be changed at any time — an analysis already running finishes into the folder it started in. When the program restarts, the last work folder and its most recent case open. Organise by date with the work-folder names, by study with the cases and by kind of analysis with the analysis folders.

3.9 New in v5

ItemWhat changed
Choosing the workspace The Workspace of the Home tab sets the root of all work folders on any disk (for example D:\SimData\MPSim), like the work directory of a simulation project. The choice is kept for the next start, and analyses in progress finish where they started.
Results as each analysis finishes Once the structure exists, each finished analysis adds its figure to a small window over the 3D/2D View, and the Result Viewer shows the analyses finished so far ("provisional" beside the title). The figures are drawn by a separate process and do not slow the run — the measured run was even 9 % faster, because the figures are no longer drawn all at the end.
Solver convergence Problems solved at the same time (conduction per direction, the seven elastic loads, the design points of a calibration) are drawn as separate curves. A single curve standing still is the slow problem.
Structure generation The overlap removal runs in parallel on all cores and ends after a number of steps, not a time, so the same input gives the same structure whatever the RVE size or the speed of the PC (chapter 5).
3D display Voxels draws the voxels of the analysis without any reduction (GPU volume rendering). Smooth shows a smooth surface built for every particle (chapter 26).
New analyses and features Viscosity and flowability (chapter 13), moisture uptake, diffusion and swelling and the properties above Tg (chapter 14), Calibration (chapter 30).
